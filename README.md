# 闸机离线补传 · 行程整理

公交数据工程师用于整理闸机离线补传刷卡 CSV 的网页应用：上传补传文件后，
按卡号查看配对行程与待核查异常。Flask + SQLite，Docker Compose 一条命令启动。

## 快速开始

```bash
docker compose up --build
```

浏览器打开 **http://localhost:8000** 即可上传 CSV、查看卡号明细。
SQLite 数据落在命名卷 `app-data` 中，容器重建数据不丢。

本地开发（不用 Docker）：

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python app.py            # 监听 0.0.0.0:8000，数据库为 ./app.db（可用 APP_DB 覆盖）
```

运行测试：

```bash
python -m unittest discover -s tests -v
```

## CSV 格式

表头必需列（大小写不敏感，允许额外列，UTF-8 编码）：

| 列 | 含义 | 示例 |
|---|---|---|
| `event_id` | 事件 ID | `E1001` |
| `card_no` | 卡号 | `C001` |
| `event_time` | UTC 时间 | `2026-11-10T08:30:00Z`（也接受时区偏移或朴素时间，朴素时间按 UTC 处理） |
| `station` | 站点 | `Alpha` |
| `direction` | 进出站类型 | `in` / `out`（兼容 `entry/exit/进/出/进站/出站`） |
| `revision` | 修订号（非负整数） | `1` |

`sample_data/` 目录有五个演示文件，按编号顺序上传可看到全部规则的效果。

## 业务规则

**修订合并（每个事件只采用最高修订）**
- 批次修订高于库内 → 写入新修订，旧修订留档不再生效；
- 批次修订低于库内 → 过期数据，忽略；
- 同事件同修订内容一致 → 幂等忽略；
- **同事件同修订内容冲突（无论文件内还是与库内）→ 整批拒绝**。

**行程配对（按时间顺序逐卡扫描）**
- 进站与其后 **24 小时内首个出站** 配成一段行程（恰好 24 小时也算）；
- 未等到出站就再次进站 → 前次进站记异常「再次进站」；
- 进站后超过 24 小时才出现出站 → 进站记「超时未配对」，该出站按孤立出站处理；
- 没有可配对进站的出站 → 异常「孤立出站」；
- 数据末尾仍未配对的进站 → 异常「进站无出站」。

**一致性与更正**
- 一个批次在**单个事务**内合并：任何冲突整体回滚，上传失败原有结果保持不变，
  查询只会看到合并前或合并后的完整状态，不会新旧混合；
- 行程与异常基于「每个事件最高修订」的视图**即时计算**，因此更正卡号或时间后，
  旧卡与新卡的行程、异常自动一同更新（见 `sample_data/03_revision_update.csv`：
  `E1006` 从 `C002` 改到 `C009` 后，两张卡的页面同时变化）；
- 失败批次也会留在上传历史里（状态「已拒绝」），便于审计追溯。

## 页面

- `/` — 上传入口、卡号汇总（事件数 / 行程数 / 异常数）、上传批次历史；
- `/cards/<卡号>` — 该卡的配对行程、待核查异常、现行事件（最高修订）；
- `/healthz` — 健康检查。

## 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `APP_DB` | 容器内 `/data/app.db`，本地 `./app.db` | SQLite 数据库路径 |
| `SECRET_KEY` | `dev-secret-change-me` | 会话签名密钥，生产环境请覆盖 |
| `PORT` | `8000` | `python app.py` 直跑时的端口 |

## 代码结构

```
app.py          Flask 路由与上传事务编排
processing.py   CSV 解析、批内冲突检测、行程配对（纯逻辑，可单测）
db.py           SQLite 建表、current_events 视图、批次合并
templates/      页面模板（中文界面）
tests/          20 个单元/端到端测试
sample_data/    演示 CSV（正常 / 异常 / 修订更正 / 两类冲突）
```
